# Desktop AI Companion: Daytime Inference + Nighttime Hive-Mind Training

**Status: unverified proposal.** This document is reproduced unedited from a proposal
generated by Google Gemini and supplied by the repo owner on November 15, 2026. It is a
design idea, not an implemented, installed, or benchmarked system. None of the numeric
claims below (VRAM budgets, checkpoint latency, payload sizes, accuracy changes) have
been tested. See `feasibility-review.md` for a separate, independent assessment of what
is established, what is plausible, and what still needs verification.

---

To build a desktop AI companion that runs smoothly on a consumer GPU (8 GB–16 GB VRAM) by day and trains a shared DiLoCo + LoRA hive-mind adapter by night, the architecture needs strict VRAM isolation, graceful interruption, and tiny network payloads.
System Overview & Tech Stack
| Layer | Recommended Stack | Role in the Architecture |
|---|---|---|
| Desktop Shell & UI | Tauri v2 (Rust) + Three.js / Live2D | Ultra-low RAM footprint (~40 MB), transparent always-on-top overlay, system tray controls. |
| Daytime Inference | llama.cpp (GGUF Q4_K_M) + hot-swappable LoRA | Fast, low-VRAM local inference (~2.5–3.5 GB VRAM for a 3B–4B model) with instant adapter hot-reloading. |
| Nighttime Trainer | Python Sidecar (Unsloth / PEFT + bitsandbytes) | Runs 4-bit QLoRA (rank r=16) when idle. Fits inside ~5–6 GB VRAM for a 3B–4B model. |
| Local Data & State | SQLite (encrypted local store) | Logs anonymized preference pairs (chosen vs. rejected) and synthetic self-play rollouts locally. |
| Coordinator Server | FastAPI (Python) + Redis / S3 | Accepts compressed LoRA pseudo-gradients (safetensors), runs validation + trimmed-mean aggregation, and serves global adapter updates. |
1. The Dual-Mode GPU Lifecycle (Day vs. Idle)
Because consumer GPUs cannot hold both a loaded inference engine and a backward-pass training graph simultaneously without spilling into slow system RAM, the Rust daemon acts as a strict GPU state machine:
 * Active Mode (Daytime):
   * The Python training worker is completely unloaded (0 MB VRAM).
   * llama.cpp holds the frozen 4-bit base model (e.g., Qwen2.5-3B or Gemma-3-4B) plus the latest global LoRA adapter (global_hive_v42.gguf) and an optional personal style LoRA.
   * When the user interacts with the companion (accepts a suggestion, regenerates a bad reply, or completes a mini-task), the app writes a DPO (Direct Preference Optimization) pair to local SQLite.
 * Idle Trigger (Night / AFK):
   * The Rust daemon monitors OS idle time (GetLastInputInfo on Windows / CGEventSourceSecondsSinceLastEventType on macOS), AC power status, and NVML/ROCm GPU utilization (< 15% for 10+ minutes so it never interrupts a game or video render).
   * Once triggered, Rust gracefully shuts down the llama.cpp server (freeing all VRAM) and spawns the Python QLoRA Worker.
 * Instant Preemption:
   * The moment the user moves the mouse or hits a hotkey, Rust sends SIGTERM to the Python trainer, saves the current step checkpoint to disk in < 500ms, clears VRAM, and relaunches llama.cpp.
2. The Federated DiLoCo Loop (How the Hive-Mind Learns)
Instead of syncing gradients every step (which requires data-center bandwidth), each desktop client acts as an independent DiLoCo island:
 * Pull Global State: The worker fetches the latest global LoRA weights (\theta_{\text{global}}) from the coordinator (~15–40 MB for a rank=16 adapter).
 * Local Inner Optimization (H = 100\text{–}250 steps):
   * Using AdamW locally on a mix of the user's local preference pairs (50%) and a shared curriculum batch of reasoning/tool-use tasks (50%) to prevent catastrophic forgetting, the PC trains its local LoRA matrices (A and B).
   * Gradient checkpointing and batch size 1 with gradient accumulation keep peak VRAM under 6 GB.
 * Compute & Compress Pseudo-Gradient:
   * Once local steps finish (or when the user wakes the PC), the worker computes the delta: \Delta \theta = \theta_{\text{local}} - \theta_{\text{global}}.
   * To keep uploads tiny and protect privacy, the worker applies Top-K sparsification (keeping only the top 10–20% largest weight changes) + 8-bit quantization, shrinking the upload payload to ~2–5 MB, and adds light differential privacy noise so individual chat phrases cannot be reverse-engineered from the weights.
 * Outer Aggregation on the Coordinator:
   * The FastAPI coordinator collects deltas asynchronously from active companions.
   * Before merging, it runs a Byzantine-robust check (cosine-similarity filtering + coordinate-wise trimmed mean) to drop poisoned or corrupted updates, evaluates the candidate merged adapter against a held-out benchmark suite, and applies an Outer Nesterov Momentum step to publish global_hive_v43.
3. Making the Learning Loop Visible in the UI
To make the distributed training feel like a rewarding Tamagotchi mechanic rather than invisible background work:
 * Dream State Animation: When the PC enters idle training mode, the desktop companion visually curls up and enters a glowing "Dreaming / Syncing" animation with a subtle VRAM/progress tooltip.
 * Morning Sync Changelog: When the user wakes their PC and the companion pulls the new global adapter, it greets them with a generated summary of what the collective learned overnight (e.g., "Synced with 412 companions overnight — +3.2% better at Python debugging and shell commands").
